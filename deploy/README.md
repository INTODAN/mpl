# Deploying the lobby

The lobby runs on its own name, `https://lobby.<domain>`, and shares a VM with its **tenants**, the games whose database lives there:

```text
players, games ──https──▶ CloudFront (lobby.<domain>, ACM certificate)
                              │
                              ▼
                         Lambda "mpl" (cmd/lobby-lambda, Function URL, streamed)
                              │  Postgres over TLS, Centrifugo's HTTP API
                              ▼
browsers ──wss──▶  Lightsail VM (vm.<domain>, static IP), Docker Compose:
                     Postgres:   the lobby's database "lobby", and one per tenant
                     Centrifugo: WebSockets; its subscribe proxy calls centrifugo_proxy_url
games ──────────▶  their own database on the VM, and Centrifugo's API (games are trusted)
```

- **Terraform** ([`terraform/`](terraform/)) owns the AWS side: the lobby Lambda and its role, CloudFront and the certificate for `lobby_hostname`, the VM (instances, static IP, firewall), the database backups' bucket and key, the alarms, and the role the Deploy workflow assumes. Its state is in the deploy bucket under `mpl/`.
- **Ansible** ([`ansible/`](ansible/)) owns the VM: Docker, Postgres with the lobby's database and each tenant's, Centrifugo with its Let's Encrypt certificate for `vm.<domain>`, the read-only admin role, the daily backups, and the settings it writes for the lobby (`deploy/local/lobby.env`) and for each tenant (`deploy/local/tenants/<key>/tenant.env`).
- **The deploy bucket** keeps what any machine needs to deploy, under `mpl/` ([`deploy_files.py`](deploy_files.py)).
- **The Deploy workflow** ([`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml)) runs the same scripts from GitHub, on `main` only, when someone starts it.

Nothing deploys on its own. Merging a pull request deploys nothing; every deploy is started by hand.

The deployment is game-neutral like the rest of the repository: a game appears only in the tenants' settings, which live in the deploy bucket. This README names [Island Battles](https://github.com/INTODAN/island-battles-go), the first tenant, only as an example.

## The deploy bucket

A private, versioned S3 bucket in the account, which this deployment may share with another one, such as the game's whose VM it took over. `MPL_DEPLOY_BUCKET` names it, on a person's machine and as the repository variable `DEPLOY_BUCKET` in the workflow. Everything of this repository's lies under `mpl/`; nothing here reads or writes anything else in the bucket, and the deploy role may write only there:

| Key | What |
|---|---|
| `mpl/terraform/terraform.tfstate` | Terraform's state (and its `.tflock` during a run). It holds the Lambda's settings and the backup key: secrets. |
| `mpl/files/…` | `deploy/local/`, synced by `scripts/aws.sh` and `scripts/vm.sh` before and after each run: `aws.tfvars`, `vm.yml`, `secrets/`, `lobby.env`, `smoke-session.json`. |
| `mpl/plans/<run ID>/` | A plan the Deploy workflow saved. The apply deletes it; a later plan run deletes those older than 3 days. |
| `mpl/tenants/<key>/tenant.env` | What each tenant needs from the lobby and the VM ([Tenants](#tenants)). The VM deploy writes it; the game's own deploy reads it. |

`scripts/deploy-files.sh status|pull|push` syncs `deploy/local/` by hand; a file changed on both sides since the last sync is a conflict, which `--force` settles. The build, plans, dumps and the tenants' files stay on the machine, outside the sync.

The bucket isn't created here: it exists already. For a deployment of its own, create a private, versioned, SSE-S3 bucket with public access blocked and a policy that refuses plain HTTP, and name it in `MPL_DEPLOY_BUCKET`.

## Settings

| File in `deploy/local/` | From | Used by |
|---|---|---|
| `aws.tfvars` | [`aws.example.tfvars`](aws.example.tfvars); every variable is described in [`terraform/variables.tf`](terraform/variables.tf) | `scripts/aws.sh` |
| `vm.yml` | [`vm.example.yml`](vm.example.yml) | `scripts/vm.sh` |
| `secrets/` | generated by the first VM deploy, or copied from the VM taken over | the VM deploy |
| `secrets/database_backups.json` | written by every `scripts/aws.sh` apply | the VM deploy |
| `lobby.env` | written by the VM deploy | Terraform, as the Lambda's environment |
| `tenants/<key>/tenant.env` | written by the VM deploy | published to `mpl/tenants/<key>/` |

Tools on a person's machine: Terraform 1.11 or newer, the AWS CLI, Python 3, Go (the migrations and the build), [uv](https://docs.astral.sh/uv/) (the smoke test) and Ansible (`uv tool install ansible-core`). The workflow installs them itself.

## Taking over a running VM

The first deployment takes over a VM that another configuration created and still deploys: the game's, which ran the lobby in its own process until now. Its Terraform keeps the VM in its state until [the cutover](#the-cutover), and removes it there with `removed` blocks, not a destroy. Nothing switches over here: the game keeps its in-process lobby, Centrifugo keeps calling it, and the VM keeps serving both.

What makes the takeover safe:

- **The plan imports, and changes nothing.** With `adopt_vm = true`, `import` blocks ([`terraform/vm.tf`](terraform/vm.tf)) bring every instance, the static IP and its attachment into this state. [`check_deploy_plan.py`](check_deploy_plan.py) refuses a plan that would change anything it imports, or that changes any other Lightsail resource in the same plan, before it is saved or applied: the plan must show them imported with **0 to change and 0 to destroy**. Lightsail can't import a firewall, so `manage_vm_firewall = false` leaves the firewall to the other configuration until the cutover, and the checker refuses a plan that would create one. A key pair can't be imported either; `ignore_changes` keeps the instance's own.
- **The VM keeps what runs on it.** `vm_compose_project` and `vm_app_dir` keep its Compose project, so its containers, its Postgres volume and its paths stay the same; the deploy stops if containers of another project publish Postgres's or Centrifugo's port. Every role that logs in with its password keeps it.
- **The secrets are the running ones**, copied below: new ones would change the passwords the game's Lambda uses and invalidate every issued token.
- **Centrifugo's proxy target stays where it is.** `centrifugo_proxy_url` names the game's Function URL until the cutover.

What the first VM deploy does change on the VM: Postgres's `pg_hba.conf` and Centrifugo's configuration are written by this repository's templates, and Centrifugo now also accepts connections from the lobby's origin. Docker Compose recreates both containers once, with their data: Postgres is down for a few seconds, and Centrifugo's WebSocket clients reconnect. Run it at a quiet time. It also installs this repository's own backup beside the other configuration's, which keeps running until the cutover ([Backups](#backups)).

### Before you start

The VM must run what the other configuration deploys today, with every secret this repository copies. For Island Battles, that means section 2 of its owner checklist ([INTODAN/island-battles-go#119](https://github.com/INTODAN/island-battles-go/issues/119)) is done first: its VM deploy that generates the lobby's secrets and creates the `lobby` database, the Terraform apply that moves the lobby to that database, and its client releases, whose release redeploys the VM with that repository's Ansible. After the takeover, don't run the other repository's VM deploy (a `vm` run, or a release that redeploys the VM) until the cutover: it would write its own configuration over this one's. If one runs anyway, run this repository's `vm` target again afterwards.

Until the cutover, the game's in-process lobby and this repository's Lambda share the `lobby` database. Deploy the lobby only from a `main` whose migrations the game's pinned module version also has: a migration that only one of them knows would leave the other on a schema it doesn't expect.

### 1. Repository settings (owner)

In this repository's settings:

1. **Environments → New environment `production`**, with **Deployment branches: Selected branches → `main`**. Both roles trust only this environment's jobs.
2. **Secrets and variables → Actions → Variables:** `DEPLOY_BUCKET` (the deploy bucket's name), `AWS_REGION` (the VM's region). `AWS_DEPLOY_ROLE_ARN` follows in step 4; `AWS_APPLY_ROLE_ARN` is optional (it defaults to `mpl-github-apply` in the deploy role's account).

### 2. Copy the running secrets (owner, with administrator credentials)

Copy the secrets the VM runs with from the other deployment's part of the bucket to this one's. The other deployment's file names, for Island Battles, which keeps its files under `files/`:

```sh
export MPL_DEPLOY_BUCKET=<the deploy bucket>
old="s3://$MPL_DEPLOY_BUCKET/files/secrets"
new="s3://$MPL_DEPLOY_BUCKET/mpl/files/secrets"
for name in postgres_superuser_password postgres_lobby_password postgres_admin_password \
  centrifugo_api_key connection_token_hmac_secret lobby_proxy_secret lobby_player_token_key \
  postgres-tls/server.key postgres-tls/server.crt postgres-tls/server.csr; do
  aws s3 cp --only-show-errors "$old/$name" "$new/$name"
done
# The tenant's own: its database's password and the lobby's hook secret.
aws s3 cp --only-show-errors "$old/postgres_app_password" "$new/tenants/island-battles/postgres_password"
aws s3 cp --only-show-errors "$old/lobby_game_secret_island_battles" "$new/tenants/island-battles/game_secret"
```

The copies keep each file's content, so the sync sees them as the bucket's own. The game keeps its own copies and its other secrets (its admin key, its submit token secret), which the lobby doesn't use.

### 3. Write the settings (owner)

From the repository root, with the bucket set:

```sh
scripts/deploy-files.sh pull
cp deploy/aws.example.tfvars deploy/local/aws.tfvars
cp deploy/vm.example.yml deploy/local/vm.yml
```

In `aws.tfvars`, describe the VM exactly as it runs: `adopt_vm = true`; `vm_instances` and `static_ip_instance` as in the other configuration's `aws.tfvars`, with any zone, blueprint or bundle it sets; `static_ip_name` as `aws lightsail get-static-ips` lists it (`island-battles-vm` for Island Battles); `vm_tags` as the instance's tags (`Project = "island-battles"`, `ManagedBy = "terraform"` for Island Battles); `manage_vm_firewall = false`; and `backup_denied_roles` with the other repository's GitHub roles (`island-battles-github-deploy`, `island-battles-github-apply`). Set `lobby_hostname`, `alert_email`, `region` and `github_repository = "INTODAN/mpl"`.

In `vm.yml`: `deploy_domain` and `lobby_url`; `centrifugo_proxy_url` as the game's Function URL, its `lambda_function_url`; `vm_compose_project: island-battles`, `vm_app_dir: /opt/island-battles` and `postgres_admin_role: island_battles_admin`, as the VM runs them; and the tenant ([Tenants](#tenants)), for Island Battles:

```yaml
tenants:
  - key: island-battles
    database: island_battles
    role: island_battles
    origins: [https://island-battles.<domain>]
    # The desktop app opens WebSockets from its web view's origins.
    websocket_origins: [tauri://localhost, http://tauri.localhost]
    # The single entry that `go run ./backend/cmd/lobby-games https://island-battles.<domain>`
    # prints in island-battles-go, as YAML or JSON.
    lobby_game: {...}
```

Then `scripts/deploy-files.sh push`.

### 4. The deploy role (owner, on a machine with administrator credentials)

The Deploy workflow needs a role before it can plan, so the first apply creates only that and the certificate, from a person's machine:

```sh
scripts/aws.sh apply -target=aws_acm_certificate.lobby \
  -target=aws_iam_role_policy.github_deploy -target=aws_iam_role_policy_attachment.github_deploy_read
python3 -I deploy/github_apply_role.py create --repository INTODAN/mpl --deploy-bucket "$MPL_DEPLOY_BUCKET"
scripts/aws.sh output github_deploy_role_arn
scripts/aws.sh output certificate_validation_record
```

The plan creates 5 resources: the certificate, the lobby function's role (the deploy role may pass it), the deploy role, its policy and its read-only attachment. It imports nothing yet. The account's GitHub OIDC provider exists already (the other deployment created it); on a new account, create it once with `aws iam create-open-id-connect-provider --url https://token.actions.githubusercontent.com --client-id-list sts.amazonaws.com`.

Set the repository variable `AWS_DEPLOY_ROLE_ARN` to the role's ARN.

### 5. The certificate's DNS record (owner)

Add the CNAME that `certificate_validation_record` printed to the domain's DNS ([DNS records](#dns-records)), and keep it: ACM renews the certificate only while it stays. ACM issues the certificate a few minutes after the record resolves.

### 6. Plan and apply (an agent plans; the owner says when to apply)

A Deploy run with target `plan` and **allow_missing_lambda_settings** ticked: the lobby function is created before the VM deploy writes its settings, and answers 503 until the first lobby deploy. The plan must read:

```text
Plan: 3 to import, 22 to add, 0 to change, 0 to destroy.
```

- **imported, unchanged:** `aws_lightsail_instance.vm["<instance>"]` (one per instance), `aws_lightsail_static_ip.vm`, `aws_lightsail_static_ip_attachment.vm`. The run's log lists them under "The plan imports 3 resources, each with no change"; any change stops the run there.
- **created:** the lobby function, its Function URL and log group, its role's two attachments; the CloudFront cache policy, distribution and the certificate's validation; the backups bucket with its public access block, versioning, lifecycle and policy, the backup user, its policy and key, and the backup alarm; the alerts topic, its email subscription, the error-lines metric filter and the two Lambda alarms.
- **nothing else:** no firewall, no budget, nothing outside `mpl-*` names but the imported VM.

Then a Deploy run with target `apply` and that run's `plan_run_id`. Confirm the email that SNS sends to `alert_email`, or the alarms send nothing. The backup alarm emails until the first VM deploy backs up.

After the apply, set `adopt_vm = false` in `aws.tfvars` (the import blocks do nothing once the VM is in the state, but an instance added later couldn't be imported), and push.

### 7. The lobby's DNS record (owner)

Add `lobby.<domain>` as a CNAME of the distribution: `scripts/aws.sh output lobby_dns_record` prints it.

### 8. The VM deploy (an agent, when the owner says)

A Deploy run with target `vm`, at a quiet time. It checks the settings, the secrets, the Compose project and `vm.<domain>`; takes over the VM's Compose project; writes `lobby.env` and the tenants' `tenant.env`, and publishes those under `mpl/tenants/`; and backs every database up once. The game keeps running throughout, apart from the containers' one restart.

### 9. The first lobby deploy and the smoke test (an agent, when the owner says)

A Deploy run with target `lobby`: it builds `cmd/lobby-lambda`, migrates the lobby's database (nothing to do while it matches the game's version) and publishes the code and settings. Then target `smoke`, which checks `lobby.<domain>` end to end ([Day to day](#day-to-day)).

Then check by hand: `https://lobby.<domain>/lobby/v1/jwks.json` answers with the same key the game publishes; the lobby page loads at `https://lobby.<domain>/lobby/ui/` and lists the game; the game's own site and its lobby work as before. `lobby.<domain>` isn't announced to players until the cutover: lobbies created there call the game's hooks, but the game still expects its own lobby until then.

## The cutover

The game's own change (INTODAN/island-battles-go#232) moves its clients to `lobby.<domain>` and lets go of the VM. This repository's side, in this order:

1. **Centrifugo's proxy:** set `centrifugo_proxy_url` in `vm.yml` to this deployment's Function URL (`scripts/aws.sh output function_url`), and run the `vm` target. Centrifugo restarts and calls the lobby from then on.
2. **The firewall,** once the game's Terraform has removed it from its state with a `removed` block (not a destroy): set `manage_vm_firewall = true`, plan and apply. The plan creates `aws_lightsail_instance_public_ports.vm["<instance>"]`, which writes the same three rules the VM has (22, 443 and Postgres); check them in the plan against the Lightsail console first.
3. **The old backup:** once the game's Terraform no longer needs it, stop the other configuration's backup timer on the VM (`systemctl disable --now <its timer>`; `island-battles-backup.timer` for Island Battles). This repository's own backup keeps running.
4. Optionally, set the game's `origins` and `websocket_origins` to what its clients use from then on, and run the `vm` target.

The account's GitHub OIDC provider stays in the game's configuration, which created it: this deployment's roles trust it too, so the game must keep it, or drop it from its own state with a `removed` block, never destroy it. Until the cutover, the game's database backups are in its own bucket, which this repository's GitHub roles can read through `ReadOnlyAccess` unless that bucket's policy denies them too (`mpl-github-deploy`, `mpl-github-apply`), as this one's denies the game's.

## Tenants

A tenant is a game with a database on the VM. Each entry of `tenants` in `vm.yml` gives:

| Field | What |
|---|---|
| `key` | The game's key in the lobby: lowercase letters, digits and hyphens. It names the tenant's secrets and its folder in the bucket. |
| `database`, `role` | Its database and the role that owns it. An existing database and role are kept as they are; a role that can't log in with its password gets it. |
| `origins` | Its sites, as `https://host`: the lobby's player API answers them with CORS (`LOBBY_ALLOWED_ORIGINS`), and Centrifugo accepts their WebSockets. |
| `websocket_origins` | Further origins for Centrifugo only, such as an app's web view. Optional. |
| `lobby_game` | Its `LOBBY_GAMES` entry ([README](../README.md#binding-a-game-over-http)), with the same `key` and with `secret_env` `LOBBY_GAME_SECRET_<KEY>`, the key in upper case with `_` for `-`. |

The VM deploy checks each entry before it changes anything, creates the database and role, generates the tenant's secrets (with `-e app_generate_secrets=true` the first time), lists the game in the lobby's `LOBBY_GAMES` and `LOBBY_ALLOWED_ORIGINS`, admits the role in `pg_hba.conf`, lets the admin role read the database, and includes it in the daily backup. It writes `deploy/local/tenants/<key>/tenant.env` and publishes it as `mpl/tenants/<key>/tenant.env`:

```sh
DATABASE_URL=postgres://<role>:<password>@vm.<domain>:5432/<database>?sslmode=require
DATABASE_HOST, DATABASE_PORT, DATABASE_NAME, DATABASE_ROLE, DATABASE_PASSWORD
LOBBY_URL=https://lobby.<domain>
LOBBY_GAME_KEY=<key>
LOBBY_GAME_SECRET=<the shared secret of the lobby's hooks and the game API>
CENTRIFUGO_API_URL=https://vm.<domain>/api
CENTRIFUGO_API_KEY=<Centrifugo's API key: games publish with it>
CENTRIFUGO_PUBLIC_URL=wss://vm.<domain>/connection/websocket
```

The game's deploy reads it from the bucket, with read access to `mpl/tenants/<key>/`. The tenant migrates its own database; the lobby's deploys never touch it. Adding a tenant: add the entry, run the `vm` target from a person's machine with `scripts/vm.sh deploy "$(scripts/aws.sh output static_ip)" -e app_generate_secrets=true` (only the new tenant's secrets are generated; the others stay), then deploy the lobby, which picks up the new `LOBBY_GAMES`. The tenants' connections count against Postgres's ([Postgres connections](#postgres-connections)).

## DNS records

DNS is outside AWS, so the records are added by hand:

| Record | Value | Output |
|---|---|---|
| ACM's validation CNAME | as printed | `scripts/aws.sh output certificate_validation_record` |
| `lobby.<domain>` CNAME | the distribution's domain | `scripts/aws.sh output lobby_dns_record` |
| `vm.<domain>` A | the static IP | `scripts/aws.sh output static_ip`; it exists already for a VM taken over |

Keep CAA records, if the domain has any, allowing `amazon.com` (the certificate) and `letsencrypt.org` (Centrifugo's).

## Deploying from GitHub Actions

The Deploy workflow runs on `main` only, in the `production` environment, when someone starts it (**Actions → Deploy → Run workflow**). Its targets:

| Target | Role | Does |
|---|---|---|
| `plan` | deploy | Removes saved plans older than 3 days, builds the lobby and plans every resource, refuses a plan that imports with a change, and saves the plan under `mpl/plans/<run ID>/`. The run's summary shows it. `allow_missing_lambda_settings` is for the very first apply. |
| `apply` | apply | Applies the plan that `plan_run_id` saved, if `main` hasn't moved since; refuses one that destroys an instance, the static IP, a disk or the distribution unless `allow_destroy` names each; migrates first when the plan publishes the lobby. |
| `vm` | deploy | `scripts/vm.sh deploy` to the static IP. |
| `lobby` | deploy | `scripts/aws.sh deploy`: builds, migrates and publishes the lobby; refuses a plan that touches anything but the lobby. |
| `smoke` | deploy | `scripts/vm.sh smoke`. |

The deploy role ([`terraform/github.tf`](terraform/github.tf)) reads the account and may write only the lobby function's code and settings, the bucket's `mpl/`, and get a temporary SSH key for the VM. The apply role ([`github_apply_role.py`](github_apply_role.py)) lives outside Terraform and may change Lightsail, Lambda, logs, alarms, SNS, ACM, CloudFront, buckets and IAM roles and users named `mpl-*`, and the bucket's `mpl/`; it can't change itself. Run `github_apply_role.py create` again after changing it.

Agents start these runs only when the owner asks ([AGENTS.md](../AGENTS.md#deploying)): a `plan`, a summary of what it imports, creates, changes and destroys, and an `apply` only on the owner's word.

## Day to day

- **A lobby change:** merge, then the `lobby` target. The plan behind it may only create or update the lobby's own resources.
- **A change to the VM's configuration** (`deploy/ansible/`, or `vm.yml`): the `vm` target. It's safe to run again.
- **A change to `deploy/terraform/`:** `plan`, read it, `apply`.
- **The smoke test** (`smoke`, or `scripts/vm.sh smoke`) goes through `lobby.<domain>`: `/healthz`, the JWKS, the lobby page and its game catalog, a guest credential that it saves in `deploy/local/smoke-session.json` and reuses (after a move, a credential that still works shows the data came along), a connection token, an authenticated GET through CloudFront, and Centrifugo: a WebSocket from the lobby's origin and a subscription through the subscribe proxy.

## Backups

Every day at `app_backup_time` (02:00 UTC), the `mpl-backup` timer on the VM dumps every database, the lobby's and each tenant's, with `pg_dump`, and uploads the dumps to the backups bucket under `postgres/`, with an access key that can only upload there and count the backup. S3 keeps each dump for `database_backup_retention_days` (7). An alarm emails when no backup succeeded for 26 hours. Every VM deploy also backs up once. The log: `journalctl -u mpl-backup` on the VM. The GitHub roles, this repository's and those in `backup_denied_roles`, may never download a dump.

The backup's names (`/etc/mpl-backup/`, `/usr/local/sbin/mpl-backup`, `mpl-backup.timer`) are its own, so on a VM taken over the other configuration's backup keeps running beside it until [the cutover](#the-cutover). To restore one: download it with administrator credentials, then `scripts/vm.sh restore <ip> <dump> -e app_database=<name>`.

## Logs and alarms

The lobby logs JSON lines; Lambda keeps only warnings and errors, in `/aws/lambda/mpl` for 7 days. Two alarms email `alert_email` within the hour: a failed invocation, and an error line. They and the backup alarm are 3 of the account's 10 free alarms, and their metrics 2 of the 10 free custom metrics; the other deployment uses its own share. The account's cost budgets stay with the account's other deployment: one set per account is enough.

## Postgres connections

Postgres keeps its default of 100 connections. Every Lambda instance of the lobby keeps a pool of `database_max_open_connections` (2), and at most `reserved_concurrency` (5) run. Terraform refuses settings where those and `tenant_database_connections` (20: one game of 5 instances with two pools of 2) leave fewer than `postgres_spare_connections` (10) free. Raise `tenant_database_connections` when a tenant opens more.

## Secrets

The VM deploy generates each secret once, on the machine that deploys, into `deploy/local/secrets/`, and every later deploy reuses it; a deploy that misses one stops, unless `-e app_generate_secrets=true` lets it generate the missing ones. Losing them would change every password and key. They are:

| File | What |
|---|---|
| `postgres_superuser_password` | Postgres's `postgres` user, which only connects inside the container. |
| `postgres_lobby_password` | The lobby's role. |
| `postgres_admin_password` | The read-only admin role, for the admin MCP server. |
| `centrifugo_api_key` | Centrifugo's HTTP API: the lobby and the tenants publish with it. |
| `connection_token_hmac_secret` | Signs Centrifugo's connection tokens. |
| `lobby_proxy_secret` | The header of Centrifugo's proxy calls. |
| `lobby_player_token_key` | The Ed25519 seed that signs player tokens. |
| `postgres-tls/` | Postgres's self-signed certificate for `vm.<domain>`. |
| `tenants/<key>/postgres_password` | A tenant's role. |
| `tenants/<key>/game_secret` | The shared secret of the lobby's hooks and a tenant's game API calls. |

## Rotating the player token key

Tokens last at most 15 minutes, and games verify them with the JWKS. To rotate: note the current `kid:seed` (`LOBBY_PLAYER_TOKEN_KEYS` in `deploy/local/lobby.env`), move `deploy/local/secrets/lobby_player_token_key` aside, and deploy the VM with `-e app_generate_secrets=true -e '{"lobby_player_token_previous_keys": ["<old kid>:<old seed>"]}'`, then the lobby. The new key signs; the old one still verifies. After 15 minutes, deploy the VM and the lobby again without the previous key.

## Dumps, restores and moving to a new VM

- `scripts/vm.sh dump <ip> [-e app_database=<name>]` dumps the lobby's database, or a tenant's, to `deploy/local/dumps/`.
- `scripts/vm.sh restore <ip> <dump> [-e app_database=<name>]` restores into an empty database; `-e app_restore_replace_existing=true` replaces one that has tables, after dumping it.

Moving to a new VM: add the new instance to `vm_instances`, plan and apply; deploy the new VM with `-e vm_static_ip=<static IP>` (its hostname still points at the old one); dump every database from the old VM, the first with `-e app_dump_lock_writes=true`, which locks every role out of it; restore each into the new VM; set `static_ip_instance` to the new instance, plan and apply, which moves the static IP; deploy the new VM again; check with the smoke test; then remove the old instance from `vm_instances`, plan and apply with `allow_destroy` naming it.

## Checks

None of these needs AWS credentials or a VM, and CI's Deploy job runs them all:

```sh
python3 -I -m unittest discover -s deploy -p 'test_*.py'   # needs ansible-playbook
cd deploy/ansible
ansible-galaxy collection install -r requirements.yml -p .collections
ansible-playbook -i localhost, --syntax-check site.yml
ansible-lint
cd ../terraform
terraform fmt -check -recursive && terraform init -backend=false && terraform validate && terraform test
```

- [`test_check_deploy_plan.py`](test_check_deploy_plan.py): the plan checker on plans shaped like `terraform show -json`'s, the takeover's imports among them.
- [`test_deploy_files.py`](test_deploy_files.py): the bucket sync, the `mpl/` prefix, publishing the tenants' settings and expiring old plans.
- [`test_vm_templates.py`](test_vm_templates.py): the VM's settings checks and every template, rendered by Ansible itself ([`ansible/tests/render.yml`](ansible/tests/render.yml)) with a VM taken over and two tenants.
- [`test_database_backup.py`](test_database_backup.py): the backup script, with fake commands and AWS clients.
- [`test_github_apply_role.py`](test_github_apply_role.py): the apply role's policies.
- [`terraform/tests/`](terraform/tests/): the configuration's logic with mocked providers: the Lambda's settings, CloudFront, the VM taken over or new, the backups' policy and the deploy role.
